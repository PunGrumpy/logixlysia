---
title: Use Logixlysia with Elysia 2
description: Which Logixlysia version to install for Elysia 2, and what to change in your app
---

[Elysia 2 "DayDream"](https://elysiajs.com/blog/elysia-20) changes route arguments, error handlers, WebSocket setup and the shape of `status()`, so one Logixlysia build can't support both Elysia 1.4 and Elysia 2. This page shows which Logixlysia version to install and what to change in your app when you upgrade.

## Compatibility

| Elysia | Logixlysia | npm tag | Install |
| --- | --- | --- | --- |
| `1.4.x` | `6.x` | `latest` | `bun add logixlysia` |
| `>= 2.0.0-beta.32` | `7.x-next` | `next` | `bun add logixlysia@next elysia@next` |

The `next` line follows the Elysia 2 beta and can break again before Elysia 2 is stable. Pin `elysia` to an exact beta version and upgrade it together with Logixlysia.

Elysia's codemod rewrites most of an app for you: `bunx @elysia/codemod@latest`.

## What to change in your app

Logixlysia's own API stays the same. The changes below are Elysia's.

### Lifecycle hooks keep their names

Early Elysia 2 betas dropped the `on` prefix (`setup`, `request`, `afterHandle`). Elysia 2.0.0-beta.32 restored the 1.4 names, and Logixlysia registers `onStart`, `onStop`, `onRequest`, `onAfterHandle` and `onError`, as on the 6.x line. Two things did change:

- `.as('scoped')` is `.as('plugin')`.
- The `{ as: 'scoped' }` option on a single hook is deprecated. Pass the scope as the first argument instead: `.onBeforeHandle('plugin', fn)`, `.onError('global', fn)`.

In `onAfterHandle` and `mapResponse`, read the handler's return value from `context.responseValue`. Elysia 2 removed `context.response`.

### Hooks come before the handler

Route hooks and schema now go before the handler:

```ts
// Elysia 1.4
app.get('/', () => 'ok', { detail: { summary: 'Root' } })

// Elysia 2
app.get('/', { detail: { summary: 'Root' } }, () => 'ok')
```

Routes with two arguments (`.get('/', handler)`) don't change.

### `resolve` is gone

Elysia 2 removed `resolve`, on routes and in macros. Return a `status()` from a macro's `beforeHandle` to answer early, or from `derive`. Logixlysia creates `ctx.log` in `derive`, so it is available in route handlers and in `beforeHandle` and `afterHandle` route hooks. An `onError` handler's context carries `store` but no derived values, so log there through `store.logger`.

### Error handlers have no `code`

Elysia 2 removed the `code` string from the error context. Pass an `Error` class to `.onError()` to handle one class. For every other error, pass only a function and narrow with `instanceof`:

```ts
import { NotFound } from 'elysia'

class MyError extends Error {}

app
  .onError(NotFound, ({ error }) => {
    /* handle 404s */
  })
  .onError(({ error }) => {
    if (error instanceof MyError) {
      /* ... */
    }
  })
```

Elysia 2 sends errors as [RFC 9457](https://www.rfc-editor.org/rfc/rfc9457) problem documents (`application/problem+json`). A thrown `Error` answers 500 even when the handler set `set.status` first, and Logixlysia logs the 500 the client got. `status()` results are `ElysiaStatus` objects with `status` and `response` fields; the 1.4 `code` field is gone.

### WebSocket is opt-in, and `ws.data` is gone

`.ws()` throws at build time unless the app registers `elysia/websocket`. Elysia 2 also merges the route context into the socket object, so `ws.data.store` from 1.4 is now `ws.store`:

```ts
import { Elysia } from 'elysia'
import { websocket } from 'elysia/websocket'
import logixlysia from 'logixlysia'

const logging = logixlysia()

interface ChatWs {
  send(data: unknown): void
}

const app = new Elysia()
  .use(websocket())
  .use(logging)
  .ws('/ws', {
    ...logging.wrapWs('/ws', {
      message(ws, message) {
        ;(ws as unknown as ChatWs).send(message)
      },
      open(ws) {
        logging.store.logger.mergeContext(ws, { room: 'lobby' })
      }
    })
  })
```

The Node adapter moved from `@elysiajs/node` to `@elysia/node`, which has a named `node()` export. The OpenAPI plugin for Elysia 2 is `@elysia/openapi`. Official Elysia 2 plugins publish under the `@elysia` npm scope, and `@elysiajs` packages stay on 1.x.

### Other Elysia 2 changes that affect plugins

- Elysia 2 removed `aot: false` (dynamic mode) and always compiles ahead of time.
- A `set.headers['set-cookie']` array is sent next to the cookies of a returned `Response`; Elysia 1.4 dropped it. Response-phase enrichers see the merged list.
- In Elysia 2.0.0-beta.32, registering any `onAfterResponse` hook makes Elysia tee generator responses through a plain iterator, and `sse()` loses its `text/event-stream` framing. Logixlysia registers no `onAfterResponse` hook; if your app does, SSE routes answer as `text/plain` until Elysia fixes this.

### `app.store` is gone from the instance

Elysia 2 instances no longer expose `store`. The Logixlysia plugin object carries its own, so code outside a request reads `logging.store.logger` and `logging.store.pino` from the plugin instead of from the app. Inside a request, `store.logger` and `store.pino` on the context are unchanged.

## What stays the same in Logixlysia

These work the same way as on the 6.x line: `logixlysia(options)`, the `preset` and `config` options, `store.logger`, `ctx.log`, `useLogger()`, `createLogger()`, `plugin.wrapWs`, sampling, enrichers, the observability adapters, and the `logixlysia/otel` and `logixlysia/ai` subpaths. Streamed and `sse()` responses are timed until their body ends, and a body cancelled by the client is logged when the cancel arrives.
