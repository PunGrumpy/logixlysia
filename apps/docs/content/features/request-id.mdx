---
title: Request ID
description: Generate or honor unique request identifiers across requests and responses
---

Logixlysia automatically generates or retrieves unique request identifiers (request IDs) and attaches them to the request context, response headers, and log outputs.

## Basic usage

Enable the request ID feature with `requestId: true`. The default configuration uses the `X-Request-Id` header and a UUID v4 generator.

```ts
import { Elysia } from 'elysia'
import logixlysia from '@pori15/logixlysia'

const app = new Elysia().use(
  logixlysia({
    config: {
      requestId: true,
    },
  })
)
```

## Production preset

The `prod` preset enables `requestId` automatically:

```ts
const app = new Elysia().use(
  logixlysia({
    preset: 'prod', // requestId is enabled automatically
  })
)
```

## Custom configuration

For advanced use cases, pass a configuration object instead of a boolean:

```ts
const app = new Elysia().use(
  logixlysia({
    config: {
      requestId: {
        // Custom header name to read from / write to
        header: 'X-Correlation-Id',
        // Custom request ID generator function
        generator: () => `req-${crypto.randomUUID()}`,
      },
    },
  })
)
```

### Options

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `enabled` | `boolean` | `true` | Turn request ID generation on or off when using object configuration. |
| `header` | `string` | `'X-Request-Id'` | The header key to read on incoming requests and to set on responses. |
| `generator` | `() => string` | `crypto.randomUUID` | A function that returns a unique string to use as the request ID. |

## How it works

1. On the request, the plugin reads the configured header (default `X-Request-Id`) from the incoming `Request`.
2. If absent, the `generator` function produces a fresh ID.
3. The ID is stored in the per-request context bag under `requestId`.
4. On the response (`afterHandle` hook), the ID is echoed back in the response header.
5. On error responses, the same ID is included in the response header and in the error log context — enabling trace correlation for failed requests.

## Log formatting

Output the request ID in your custom log format using the `{requestId}` placeholder:

```ts
const app = new Elysia().use(
  logixlysia({
    config: {
      requestId: true,
      customLogFormat: '{method} {pathname} - Request ID: {requestId}',
    },
  })
)
```

If request ID is disabled or not present, the token renders as an empty string.

## Cross-service tracing

Pair the request ID with `autoRedact: true` so the `authorization` and `cookie` headers are scrubbed from the access log, but the request ID is still attached for grep-ability:

```ts
logixlysia({
  config: {
    requestId: true,
    autoRedact: true,
    customLogFormat: '[{requestId}] {method} {pathname} {status} {duration}ms',
  },
})
```

For distributed tracing, layer OpenTelemetry on top with `injectTraceContext` (see [OpenTelemetry](/docs/integrations/otel)). Request IDs and trace IDs are independent — the request ID is your application-level correlation key, and the trace ID is the OTel-level one.
